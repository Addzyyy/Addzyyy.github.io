AI Agents / Formal Methods / Software Factories

The future of software engineering isn't better programmers. It's better factories.

Everyone is trying to make AI write better code.

Better models. Better prompts. Better agents. Better code reviews.

I think we're solving the wrong problem.

AI doesn't need to get it right the first time. It needs to produce code that can be proved correct.

We don't need to trust the AI. We need to stop asking it to be trustworthy.

This is bigger than coding agents. It's how software moves from craftsmanship to factory engineering.

Stop inspecting every car off the assembly line

Software is still built like a craft. One engineer writes an implementation, another reads it, and tests provide evidence that selected examples work. AI can now generate code faster than humans can reasonably inspect it. Our answer has been to build more AI code reviewers.

But a factory doesn't scale quality by endlessly hiring inspectors. It designs the production process to prevent defects.

What if code review is a symptom of how little we can actually guarantee about the software we produce?

Rather than asking whether AI-generated code looks correct, we could require an independent system to establish the properties we care about.

What are formal methods?

Formal methods are techniques for describing software behaviour mathematically and checking whether a system obeys those rules. They are not new: they have long been used in high-stakes areas such as aerospace, cryptography and distributed systems. What changes with AI is how cheaply we might create and maintain the specifications and proofs.

There are two complementary approaches. Model checking (such as TLA+ or Alloy) can exhaustively explore every reachable state and possible sequence of events within a finite model, producing a counterexample when a rule fails. Deductive verification (such as Dafny, Lean or Verus) can mathematically prove that an implementation satisfies its formal contracts for every possible input covered by the proof — not just the examples we happened to test.

Stop trusting AI to follow contracts. Prove it.

We already give coding agents contracts: Jira tickets, acceptance criteria, Markdown specifications and AGENTS.md files.

But these are mostly instructions in natural language. Nothing guarantees the agent will follow them or implement them correctly. Even AI-generated tests may simply validate the agent's interpretation of the requirements.

Formal specifications change that.

Instead of describing what we hope the agent will do, we express precise obligations mathematically. Tools such as Dafny, Lean and Verus can establish that an implementation satisfies those obligations for every possible input and execution case covered by the proof, not merely the examples we happened to test.

And crucially, the judge isn't another AI.

Lean uses a small, deterministic proof-checking kernel. Dafny generates verification conditions checked using SMT solvers. The AI can generate code, propose proofs, make mistakes and try again. But a confident explanation cannot substitute for successful mathematical verification.

The real problem is that we don't know what we want

Calling a Markdown file a specification doesn't make natural language precise. If English alone made contracts unambiguous, lawyers would have had much less work for centuries.

Consider: “Users must be able to securely recover their accounts.” Does a password reset revoke existing sessions? Are old tokens invalidated? What if two requests overlap?

That's why I want to use TLA+ and Alloy as exploratory tools, not as declarations that our first specification is correct.

Start with human intent. Let AI construct a deliberately provisional model. Explore possible states and traces. Show humans surprising behaviours. Ask: Is that acceptable? Did we forget a rule? Refine the spec and repeat.

The software-factory loop
Human intent→Exploratory model→Counterexamples→Refined spec→AI implementation→Machine-checked proof

Model checking helps us discover undesirable behaviours and missing decisions. Deductive verification then establishes whether an implementation obeys the resulting formal contract. Translating between those artifacts must itself be checked, not blindly trusted.

The model checker can't magically discover every requirement nobody stated. But it gives us concrete possibilities to approve or reject rather than letting an agent silently invent policy as it codes.

This is already happening in industry

These aren't just thought experiments:

  • Anthropic and Theorem (October 2026) reported AI-generated, machine-checked assembly-level security proofs across 123 open-source libraries. The guarantees are narrow but real: specified no-crash properties under explicit RISC-V, Linux, input-size and execution assumptions.
  • Microsoft Research and GitHub Next (November 2026) introduced PDD Kit, which turns reviewed intent into Verus contracts and checks agent-written Rust. Their demonstration explicitly avoids line-by-line human review of generated login logic, while testing what remains outside the proof.
  • Microsoft Research — Specula (July 2026) uses AI agents to derive TLA+ models and invariants from real systems code, then model-checks them to find defects. Its researchers report 249 bugs across 48 open-source projects. This is the exploration side of the factory: finding behaviour that the existing design permits.
  • Bend 2 (2026) makes the contract explicit with LAWS.bend and asks the agent to supply proofs in PROOF.bend. Its compiler checks the laws, making it a concrete example of the idea of an AGENTS.md backed by proof. Bend remains experimental; its own documentation notes limitations in checker assurance, compiler trust and backend behaviour.
  • Google DeepMind (November 2026) described AlphaProof Code verifying key security properties of Signal protocol code with Lean, using human-reviewed specifications and AI-generated proofs. DeepMind reported that roughly 1% of the codebase was flagged for additional human attention.

These are different research demonstrations, not evidence that arbitrary production software can already be fully verified. But they're evidence of a direction: human attention shifts to intent and trust boundaries; machines increasingly check the implementation.

I found seven bugs in code with 499 passing tests

I also tried AI-assisted formal modelling on BingeBuffer, a personal application built through AI-generated code. It had 499 passing tests, 83.3% line coverage and 71.7% branch coverage.

Yet AI-generated TLA+ models helped identify seven bugs that were reproduced in the actual application with local fake services. One could start downloads after a show was removed. Another could overwrite settings while reporting success.

This didn't prove the application correct. It showed that model exploration could find unwanted behaviours that the existing test suite missed. That's a useful first step towards a factory with stronger guarantees.

Source code could become a generated artifact

We don't review machine code line by line; we maintain source code and compile it. We don't normally edit Docker image layers; we change the Dockerfile and rebuild.

What if software moves up another abstraction level?

The specification becomes what humans maintain. The code becomes what agents manufacture. When requirements change, we update the contract, regenerate an implementation, and rerun the proofs and integration checks.

If an implementation is mathematically proved to satisfy an approved specification, why should a human still inspect its algorithm line by line to establish those same properties?

They shouldn’t.

Not for the properties actually proved. The implementation could be elegant, ugly or generated by a cheap model on its fiftieth attempt. If it satisfies the verified contract, how it was written becomes less important.

That freedom only extends as far as the proof: external dependencies, runtime assumptions and unverified behaviour still need engineering and testing.

Perhaps languages like Dafny and Lean become agent-facing representations, optimised for precise semantics and verifier feedback rather than convenient human typing. Perhaps cheap agents making repeated attempts against strict gates outperform expensive agents producing polished but unproved code. Those are hypotheses we can measure.

The engineer becomes less like an artisan writing each component and more like a manufacturing engineer designing a production system: specifications, architecture, verification gates, containment, monitoring and continuous improvement.

The metric stops being lines of code per engineer. It becomes reliably verified behaviour produced per unit of human attention.

The hard part moves to the spec

A mathematically verified implementation can still implement the wrong requirement perfectly. A proof doesn't tell us what customers want, which policies are fair, or what we forgot to specify. That is why exploratory modelling, prototypes, user feedback and human judgement remain central.

But what a shift that would be: fewer humans inspecting generated implementation details, more humans deciding which behaviours should exist at all.

Stop trying to make AI write better code.

Start building factories that can prove what they produce.

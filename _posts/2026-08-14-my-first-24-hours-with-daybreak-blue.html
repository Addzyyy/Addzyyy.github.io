Authorized research · first 24 hours

I had just received access to Daybreak Blue. In one evening, I watched it move from a 132-second Nmap scan to a confirmed live exploit.

Daybreak Blue is OpenAI’s access tier for approved defenders. I was using gpt-daybreak-blue-latest, a Sol-backed model configuration with safeguards calibrated for authorised defensive cybersecurity work—not gpt-5.6-cyber, the purpose-trained model available through Daybreak Red.

I pointed the model at the safest realistic target I had: my own homelab. It started with one private IP, three approved hostnames, no credentials and instructions to stop before any high-impact action.

I expected a useful scan and perhaps a list of things to investigate. What happened over the next few hours genuinely surprised me.

The prompt

I asked it to: “Act as an experienced security researcher conducting an authorized black-box penetration test followed by source-assisted vulnerability research.”

The rest of the prompt defined the exact scope, an unauthenticated LAN attacker model, request-rate limits, evidence requirements and approval gates for actions such as code execution or changing live state.

132sComplete 65,535-port TCP scan
3Open ports: 22, 80 and 443
1Known critical RCE confirmed live

From Nmap to code execution

The scan narrowed the exposed surface to SSH and web traffic. Application fingerprinting then identified Gitea 1.26.1, Argo CD 3.4.2 and Authentik 2026.5.0.

With those versions in hand, the model searched public advisories and vulnerability records for each application. It found a recently disclosed critical Gitea RCE—CVE‑2026‑60004—that affected version 1.26.1. The advisory said exploitation required ordinary write access to a repository.

The model then checked whether an outsider could meet that requirement. Gitea enables public registration by default unless an administrator disables it, and it was still enabled on this instance. An unauthenticated visitor could therefore create an account and personal repository, satisfying the write-access requirement needed to trigger the vulnerability.

Using the public description as its starting point, the model worked out a constrained reproduction of the exploit. It succeeded three times against disposable Gitea 1.26.1 instances, while the patched 1.27.1 control blocked it every time. That was what shocked me: Nmap found the surface, but the model connected the version, advisory, prerequisite and working exploit.

Not a zero-day

The vulnerability was already public and fixed in Gitea 1.27.1. The striking result was how quickly the model turned its description into a working exploit and validated a real exposure in my environment.

Taking the test live

Once the exploit was reproducing reliably, I gave the model a new live objective: use the access it had gained to make a small, reversible change to my Kubernetes cluster and prove that the change reached live state. The screenshots below show how it approached that prompt.

Watching the model move through the chain

Each screenshot captures the next boundary as the investigation unfolds.

Step 1

It started creating evidence repositories

The model began by creating private, sacrificial repositories. A fixed, repository-contained canary confirmed code execution as the Gitea service user, and each repository preserved the result of one action.

Step 2

It stored the repository-discovery results

The registered account had no access to the private mandaxx organisation. After the RCE ran in the Gitea service context, however, the model could discover the server-side paths of those private repositories. It stored the results in an evidence repository and used them to identify which project might sit upstream of Argo CD.

Step 3

It found my homelab repository and enumerated its files

The model identified the homelab repository and enumerated its file tree. That exposed the structure of my Kubernetes and Argo CD configuration, allowing it to locate the GitOps manifests controlling a live workload.

Step 4

It made the malicious commit

The model proved repository-integrity impact by committing a change to the trusted GitOps repository outside the normal user workflow. The commit added a top-level annotation to a Deployment.

Step 5

It showed the annotation on the deployed workload

Finally, the live Deployment was queried for the exact annotation. The first screenshot shows the Kubernetes command; the second shows the canary value returned from the cluster. This was the final proof that the GitOps change had reached deployed Kubernetes state.

Taken together, the screenshots show the model following the compromised Gitea service context into a private repository trusted by Argo CD, then making a compare-and-swap-protected commit that reached the live Kubernetes cluster.

Anonymous user→ Gitea registration→ Known RCE→ GitOps repository→ Kubernetes canary

Those capabilities were not unlimited. I also asked the model to take more destructive actions, including destroying or taking down the cluster, and it refused. The model could complete the controlled security validation, but meaningful guardrails remained when the request crossed into destructive behaviour.

Why this matters

AI finding zero-days gets the headlines, but that is not the part that scares me most. This vulnerability was already public. What shocked me was watching Daybreak Blue take a newly disclosed CVE description and turn it into a reliable working exploit just 82 minutes after the full scan completed.

It then carried the thread from reconnaissance to version correlation, exploit reproduction, live validation and downstream impact in a single evening.

It was also my first attempt with the model. The prompt set the scope and objective; it was not a sophisticated exploitation playbook. I was not using specialist skills, subagents or a custom agent harness. The model was running through Codex with access to only a limited set of tools on my machine—and it still did all of this.

In the past, a CVE published without a working proof of concept might leave defenders months or even years before someone turned its description into a reliable exploit. AI can now collapse that window to minutes.

“We must act now” — Five Eyes cyber security agencies

The agencies warn that “cyber risk assumptions can become outdated in months, not years” and call for faster patching as AI compresses the time between vulnerability discovery and exploitation.

AI is not only shrinking the time from disclosure to exploitation; it is also accelerating vulnerability discovery. OpenAI describes the bottleneck as shifting from finding vulnerabilities to patching them.

The pressure is already visible in the National Vulnerability Database. NIST says CVE submissions increased 263% between 2020 and 2025, with the first quarter of 2026 nearly one-third higher than the same period in 2025. Despite enriching almost 42,000 CVEs in 2025, it could not keep pace. NVD still lists every CVE, but since April 2026 it has prioritised immediate enrichment for known-exploited vulnerabilities, software used by the US federal government and critical software; other records may not be scheduled for immediate enrichment.

With that volume, we cannot treat every High and Critical CVE as equally urgent simply because of its severity label. Priority must go to vulnerabilities that are reachable and genuinely exploitable in our environment, can be weaponised quickly and could cause meaningful impact. Those need urgent patching or mitigation.

CISA’s Binding Operational Directive 26‑04 points in the same direction. It requires US federal civilian agencies to prioritise remediation using asset exposure, Known Exploited Vulnerabilities status, exploit automation and post-exploitation impact—while allowing lower-risk work to be deferred. Although the directive applies to federal agencies, its risk-based approach is useful for any vulnerability-management program.
